# Сценарий и замечания преподавателя

**Тема:** доступ к устройствам через файловый интерфейс и отображение файлов в память (`mmap`)  
**Команда:** Иванов, Гусев, группа 3211  
**Формат:** анимация на Manim Community, общий хронометраж 30–120 с, отдельные фрагменты по 10–30 с.

Первые три содержательные сцены обсуждены с преподавателем. Его замечания к доступу через `/dev/ttyS0` зафиксированы ниже и внесены в анимацию. Сцены об `mmap` преподаватель пока подробно не разбирал; их состав и глубину объяснения предстоит согласовать отдельно.

## Главная идея ролика

Ролик показывает **два маршрута** через файловый интерфейс:

1. **Вызовы к файлу устройства:** `open("/dev/ttyS0")` → VFS и структуры ядра → файловый дескриптор → `read(fd, …)` → обработчик TTY. Полученные UART байты проходят через serial-драйвер и буфер TTY в пользовательский буфер. Процесс использует тот же файловый интерфейс, что и для обычного файла.
2. **Отображение обычного файла:** `open("data.bin")` → `mmap(fd, …)` → область виртуальной памяти → первый доступ и page fault → страница кэша → дальнейшие обращения по адресу. Данные читаются и изменяются через память процесса.

**Связка в финале:** если файл устройства и его драйвер поддерживают отображение, `mmap(fd, …)` может дать процессу доступ к памяти, предоставляемой устройством. Учебный пример — `/dev/fb0` с простой моделью кадрового буфера. Обычный файл и файл устройства проходят через один вызов `mmap`, но за ним стоят разные механизмы: страница кэша файла или отображение памяти устройства. Поддержка `mmap` у файлов устройств не универсальна.

## Что изучено

### Маршрут A. Файл устройства → драйвер

Узел в `/dev` имеет тип `c` (символьное устройство) или `b` (блочное) и номер устройства `(major, minor)`. В Linux inode специального файла хранит этот номер в `i_rdev`, а не содержимое устройства. Для принятого примера `4:64`: `4` — major семейства TTY, `64` — minor, выделенный `/dev/ttyS0` в стандартном списке устройств Linux. Пара не является адресом. Поиск зарегистрированного символьного устройства использует полный номер и диапазоны номеров, а не только `major`. [Реестр устройств Linux](https://docs.kernel.org/admin-guide/devices.html), [исходник `chrdev_open`](https://github.com/torvalds/linux/blob/master/fs/char_dev.c).

При `open("/dev/ttyS0", O_RDWR)` ядро разрешает путь через VFS, создаёт описание открытого файла `struct file`, находит зарегистрированное символьное устройство по `i_rdev` и устанавливает его таблицу операций `file_operations` в `file->f_op`. VFS, inode, `struct file` и таблица дескрипторов процесса представлены структурами **ядра Linux**; строка кода и переменная `fd` находятся в процессе. Возвращённый `fd` — небольшое целое число, индекс таблицы дескрипторов, **не адрес** устройства и не адрес `struct file`. В схеме `fd = 3` — пример при занятых 0–2; действительный номер зависит от процесса. [Документация VFS](https://docs.kernel.org/filesystems/vfs.html), [описание `open(2)`](https://man7.org/linux/man-pages/man2/open.2.html), [структура таблицы дескрипторов](https://github.com/torvalds/linux/blob/master/include/linux/fdtable.h).

Вопрос преподавателя «точно ли в драйвере есть `open()` и `read()`?» требует разделить уровни. `open()` и `read()` в строке C — вызовы пользовательского API. В подсистеме TTY Linux таблица `tty_fops` содержит колбэки `.open = tty_open` и `.read_iter = tty_read`. У serial-драйвера нет обязательной функции с именем `read`; serial core использует другой набор операций, в том числе `tty_operations` и низкоуровневые `uart_ops`. Поэтому подпись «драйвер tty: .open(), .read()» заменена на «TTY: file_operations» с фактическими полями, а serial-драйвер показан отдельно. [Исходник TTY](https://github.com/torvalds/linux/blob/master/drivers/tty/tty_io.c), [serial core](https://github.com/torvalds/linux/blob/master/drivers/tty/serial/serial_core.c), [API serial-драйверов](https://docs.kernel.org/driver-api/serial/driver.html).

При `read(fd, buf, 8)` ядро по числу `fd` находит `struct file`, затем через `file->f_op` вызывает обработчик TTY. Принятые UART данные проходят serial-драйвер, буферизацию TTY и дисциплину линии; затем ядро копирует доступные байты в `buf` пользовательского процесса. **Вызов `read()` не обязан запускать приём байтов устройством:** они могли поступить раньше либо прийти, пока вызов ожидает данные. Полученное число байтов может быть меньше запрошенных восьми. В анимации три байта `O`, `K`, `\\n` и результат `n = 3` — учебный пример. [Буфер TTY](https://github.com/torvalds/linux/blob/master/drivers/tty/tty_buffer.c), [дисциплина линии](https://docs.kernel.org/driver-api/tty/tty_ldisc.html), [описание `read(2)`](https://man7.org/linux/man-pages/man2/read.2.html).

`ioctl` передаёт команды, которые не выражаются обычным потоком байтов. Наличие и смысл `read`, `write`, `ioctl` и `mmap` зависят от конкретного устройства и драйвера; не каждый файл устройства поддерживает все эти операции. [Документация VFS](https://docs.kernel.org/filesystems/vfs.html), [описание `ioctl(2)`](https://man7.org/linux/man-pages/man2/ioctl.2.html).

### Маршрут B. Обычный файл → виртуальная память

В предлагаемом примере процесс отображает 16 КиБ файла `data.bin` с `MAP_SHARED` и читает `p[5000]`. Для наглядности считаем размер страницы равным 4096 байтам; настоящий размер нужно узнавать у системы. Смещение 5000 попадает во вторую страницу (номер 1), на 904 байта от её начала.

В обычном ленивом отображении `mmap` создаёт область виртуальной памяти (VMA) с диапазоном адресов, правами и ссылкой на файл; сразу читать все 16 КиБ не требуется. При первом обращении, когда нужной записи таблицы страниц ещё нет, возникает page fault. Ядро проверяет VMA и права, ищет нужную страницу в кэше страниц; **только при промахе кэша** нужно читать данные из хранилища. После установки соответствия виртуальной страницы и физического фрейма инструкция повторяется. Следующие обращения к этой уже отображённой странице обычно идут без системного вызова и без отдельного копирования в пользовательский буфер. Возможны дополнительные faults, вытеснение страниц и другие варианты поведения; для ролика показан один холодный доступ. [Описание `mmap(2)`](https://man7.org/linux/man-pages/man2/mmap.2.html), [документация ядра о кэше страниц и readahead](https://docs.kernel.org/core-api/mm-api.html).

При `MAP_SHARED` изменение отображения видно другим процессам, отображающим тот же участок файла, и затем записывается обратно в файл. Для точного контроля момента записи используется `msync(..., MS_SYNC)`: вызов ждёт её завершения. **`munmap()` снимает отображение, но сам по себе не даёт гарантии синхронной записи к моменту возврата.** При `MAP_PRIVATE` запись вызывает copy-on-write: процесс получает личную копию страницы, а его изменение не попадает в файл. Для одновременных записей нескольких процессов нужна отдельная синхронизация. [Описание `mmap(2)`](https://man7.org/linux/man-pages/man2/mmap.2.html), [описание `msync(2)`](https://man7.org/linux/man-pages/man2/msync.2.html).

В текущей анимации изменённость показана цветом страницы кэша без таблицы страниц. В реальном ядре учёт грязных файловых страниц сложнее: первая запись может проходить через fault, а сброс конкретного бита PTE не является обязательным результатом каждого `msync`. Если преподаватель попросит показать PTE, эту деталь нужно вводить отдельно и не смешивать её с состоянием файловой страницы. [Документация ядра о writeback](https://docs.kernel.org/core-api/mm-api.html).

### Связка. `mmap` файла устройства

Если драйвер предоставляет операцию отображения, вызов `mmap` для файла устройства создаёт VMA и связывает адреса процесса с предоставленной драйвером памятью. В простой модели `/dev/fb0` драйвер устанавливает соответствия виртуальных страниц и страниц кадрового буфера; это **не путь через кэш страниц `data.bin`**. Конкретный механизм драйвера и момент установки PTE зависят от его реализации. `remap_pfn_range` / `io_remap_pfn_range` — возможные низкоуровневые средства, а не универсальная обязательная последовательность для всех устройств и версий ядра. [Описание `mmap(2)`](https://man7.org/linux/man-pages/man2/mmap.2.html), [API памяти ядра](https://docs.kernel.org/core-api/mm-api.html).

`/dev/fb0` — пример API fbdev, доступность которого зависит от системы. Перед записью пикселей настоящая программа узнаёт параметры экрана через `FBIOGET_VSCREENINFO` **и** `FBIOGET_FSCREENINFO`; адрес пикселя зависит от формата и `line_length` (шага строки). В учебной модели можно принять экран 16×8, 32 бита на пиксель и плотно упакованные строки, явно обозначив это условие. Также не следует обещать, что каждая запись в любой framebuffer немедленно меняет физический экран: некоторые драйверы используют теневой буфер или отложенный вывод. [API fbdev](https://docs.kernel.org/fb/api.html).

### Визуальные правила

- Постоянные цвета ролей: процесс — синий, структуры ядра — фиолетовый, драйвер — бирюзовый, оборудование — оранжевый, данные обычного файла — зелёный. Цвет ошибки/fault и цвет изменённых данных выделяются отдельно.
- Один активный путь за раз. Предыдущие блоки остаются приглушёнными, текущий шаг подсвечивается; стрелка двигается в направлении данных или вызова.
- Постоянная нижняя подпись отвечает на вопрос «что изменилось сейчас», а короткие подписи над блоками называют сущности. Важные выводы показываются на отдельной паузе.
- Условные числа (`fd = 3`, страница 4096 байт, фрейм 5, PFN видеопамяти) помечаются как пример. Нельзя изображать их как свойства любой Linux-системы.
- Стиль Core Dumped берём как ориентир по ясной схеме, тёмному фону и движению данных; графику и текст делаем самостоятельно.

## Итоги обсуждения первой части

- Показать `/dev/ttyS0` как путь к узлу устройства, а `4:64` расшифровать как major/minor; поместить запись inode в рамку ядра Linux. Убрать повторяющиеся общие фразы о пути и байтах.
- Назвать сцену `open()` инициализацией подключения и объяснить, что возвращённый дескриптор идентифицирует открытый объект. Схема уточняет: в Linux это целочисленный индекс таблицы, а не адрес.
- Явно расшифровать VFS, показать, что таблица дескрипторов, inode и `struct file` находятся в ядре, и не называть сам `fd` таблицей.
- Заменить предполагаемые «.open()» и «.read()» у драйвера на действительные обработчики `tty_fops`; serial-драйвер выделить как следующий уровень.
- Назвать сцену `read()` «жизненным циклом данных». Поместить код и буфер в рамку пользовательского процесса, убрать ошибочный значок режима ядра из пользовательской области, показывать запрос и движение данных по очереди.
- Первой сдавать на просмотр переработанную часть про `/dev`, `open()` и `read()`. Остальную часть обсудить с преподавателем позднее.

## Границы учебной модели

- Показан Linux. Для другого ядра имена структур и порядок внутренних вызовов могут отличаться. Внутренние функции Linux тоже меняются между версиями; главный предмет ролика — устойчивые отношения между интерфейсом, драйвером, VMA и памятью.
- `ls -l` показывает **выбранные** узлы `/dev`, а не исчерпывающий вывод каталога. Номера и права файлов устройств могут различаться по системе.
- Для обычного файла показаны холодный page fault и страница кэша. Страница может уже находиться в кэше; ядро может применить предварительное чтение, а для некоторых файлов действуют иные механизмы отображения.
- Аргумент `offset` у `mmap` должен быть кратен размеру страницы; длина положительна; права отображения должны согласовываться с открытием файла. Нужно проверять результат на `MAP_FAILED`. Закрытие `fd` не удаляет существующее отображение.
- Доступ к странице целиком за концом отображённого файла может привести к `SIGBUS`; доступ вне самого диапазона отображения — к ошибке адресации, обычно `SIGSEGV`. Частично заполненная последняя страница файла имеет особые правила. Эти случаи не входят в основной сюжет.
- При `MAP_SHARED` физическая страница может быть общей, но визуальный флаг D — только символ изменённости. Для надёжной записи на носитель используется `msync(..., MS_SYNC)`; `munmap` не заменяет его гарантию.
- Модель framebuffer предполагает прямой линейный 32-битный буфер. Реальный адрес пикселя рассчитывают с учётом формата и шага строки, а обновление экрана зависит от драйвера.
